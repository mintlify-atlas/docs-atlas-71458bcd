Deploying Work Time Recorder to a China mainland server eliminates cross-border latency for domestic users and satisfies the regulatory requirement that public-facing web services hosted on mainland IP addresses carry a valid ICP filing. This guide walks through every phase of the process in sequence — from purchasing infrastructure to verifying a live HTTPS deployment — using a mainland Nginx server for static hosting and Tencent CloudBase (Shanghai region) for authentication, data storage, and real-time synchronisation.

## Architecture overview

After this deployment, all traffic for domestic users stays entirely within the mainland. The CloudBase SDK is self-hosted alongside the static files, so there are no external CDN dependencies.

| Component | Role | Location |
|---|---|---|
| Static frontend | HTML/CSS/JS, PWA, vendor SDK (`cloudbase.js`) | Mainland Nginx server |
| Auth & database | CloudBase Auth + Document DB | CloudBase Shanghai (`ap-shanghai`) |
| Realtime sync | CloudBase `watch` | CloudBase Shanghai |
| ICP compliance | Domain registration & filing (备案) | Same mainland server |

**Key constraints to keep in mind before you start:**

- CloudBase static hosting **cannot** serve as the ICP filing access resource — you must purchase a separate mainland server.
- During the ICP review period the domain **must not** be pointed at the server or used to serve public web traffic.
- `config.js` contains your CloudBase environment ID. The deploy script **explicitly excludes it** from rsync uploads so it must be created manually on the server. See [Phase 5](#phase-5--deploy-frontend) below.

## Phase 1 — Server & domain setup

<Steps>
  <Step title="Purchase a mainland application server">
    In the Tencent Cloud console go to **Lighthouse Application Server → Create Instance** and choose:

    | Setting | Requirement |
    |---|---|
    | Region | Any **mainland** node: Beijing, Shanghai, Guangzhou, Nanjing, Chengdu, etc. |
    | Billing | Subscription **≥ 3 months** (ICP filing hard requirement) |
    | Spec | 2 vCPU / 2 GB RAM minimum (sufficient for pure static hosting) |
    | Image | **OpenCloudOS** or **CentOS** (provides `dnf`/`yum`) |

    Record the **public IP** and configure either a root password or an SSH key for access.
  </Step>

  <Step title="Set up passwordless SSH from your development machine (recommended)">
    The deploy script relies on SSH key authentication. Run the following on your local machine:

    ```bash
    # Generate a key if you don't have one
    ssh-keygen -t ed25519 -C "deploy-work-time-recorder"

    # Copy the public key to the server (enter root password when prompted)
    ssh-copy-id root@YOUR_SERVER_IP

    # Verify
    ssh root@YOUR_SERVER_IP "hostname && uname -a"
    ```
  </Step>

  <Step title="Register a domain">
    Register a `.com`, `.cn`, or equivalent domain from any accredited registrar (for example Tencent Cloud DNSPod). Complete **real-name verification** on the registrar side — this is a prerequisite for ICP filing. Note the domain name; it is referred to as `your-domain.com` throughout this guide.
  </Step>
</Steps>

## Phase 2 — ICP filing (备案)

ICP filing is a legal requirement before serving web traffic on a mainland IP. Do **not** point your domain's DNS A record at the server until the filing is approved. You can — and should — complete Phases 3 and 4 (CloudBase setup and local verification) in parallel while you wait.

<Steps>
  <Step title="Open the Tencent Cloud filing system">
    Navigate to the [Tencent Cloud ICP filing portal](https://cloud.tencent.com/product/ba) and click **Start Filing (开始备案)**.
  </Step>

  <Step title="Prepare your materials">
    For individual (personal) filing you will need:

    | Material | Detail |
    |---|---|
    | National ID | Front and back photo |
    | Mobile number | Real-name registered, for SMS verification |
    | Domain | Already real-name verified at the registrar |
    | Filing server | Select the mainland Lighthouse server you just purchased |
    | Identity verification | Tencent Cloud App face scan or backdrop photo (varies by province) |
  </Step>

  <Step title="Complete the filing form">
    - **Subject information**: full name, ID number, address, mobile number.
    - **Website name**: use a neutral, non-sensitive description such as "个人工时记录" (Personal Work Time Recorder).
    - **Domain**: enter `your-domain.com` exactly as registered.
    - **Access provider**: Tencent Cloud (auto-associated with the purchased server).
  </Step>

  <Step title="Wait for approval and note the filing number">
    Review typically takes **7–20 business days** depending on the province. Once approved, you will receive a filing number (备案号) — you may display this in the site footer as required.
  </Step>
</Steps>

## Phase 3 — Server initialisation

Run the following commands on the server via SSH. This can be done before ICP approval — you are only preparing the server, not yet pointing a domain at it.

```bash
# Update packages and install dependencies
sudo dnf update -y
sudo dnf install -y nginx rsync certbot python3-certbot-nginx

# Enable and start Nginx
sudo systemctl enable --now nginx
sudo systemctl status nginx

# Open HTTP and HTTPS in the system firewall
sudo firewall-cmd --permanent --add-service=http
sudo firewall-cmd --permanent --add-service=https
sudo firewall-cmd --reload

# Create the web root and set correct ownership
sudo mkdir -p /var/www/work-time-recorder
sudo chown -R nginx:nginx /var/www/work-time-recorder
sudo chmod 755 /var/www

# Disable the default Nginx site to avoid port conflicts
sudo mv /etc/nginx/conf.d/default.conf /etc/nginx/conf.d/default.conf.bak 2>/dev/null || true
sudo nginx -t && sudo systemctl reload nginx
```

<Note>
  The Tencent Cloud Lighthouse console also has a **Firewall** panel under **Security Groups**. Make sure ports 22 (SSH), 80 (HTTP), and 443 (HTTPS) are open there as well — the `firewall-cmd` commands above only affect the OS-level firewall.
</Note>

## Phase 4 — Nginx and HTTPS

**Do this only after ICP approval**, when it is safe to point the domain at the server.

<Steps>
  <Step title="Add the DNS A record">
    In your DNS control panel (e.g. Tencent Cloud DNSPod), create:

    | Type | Host | Value | TTL |
    |---|---|---|---|
    | A | `@` | Server public IP | 600 |
    | A | `www` (optional) | Same IP | 600 |

    Verify propagation before continuing:

    ```bash
    dig +short your-domain.com
    ```
  </Step>

  <Step title="Upload and configure the Nginx site template">
    The repository includes a ready-to-use template at `deploy/nginx.conf`. Copy it to the server and replace the placeholder domain:

    ```bash
    scp deploy/nginx.conf root@YOUR_SERVER_IP:/etc/nginx/conf.d/your-domain.com.conf
    ```

    Then SSH into the server and open the file in an editor to replace every occurrence of `flytime.cloud` with your actual domain. The key sections of the template are reproduced below for reference:

    ```nginx
    # HTTP → HTTPS redirect
    server {
        listen 80;
        server_name your-domain.com;
        return 301 https://$host$request_uri;
    }

    server {
        listen 443 ssl;
        http2 on;
        server_name your-domain.com;

        root /var/www/work-time-recorder;
        index index.html;

        # Let's Encrypt certificate paths (filled in by Certbot)
        ssl_certificate     /etc/letsencrypt/live/your-domain.com/fullchain.pem;
        ssl_certificate_key /etc/letsencrypt/live/your-domain.com/privkey.pem;
        ssl_protocols       TLSv1.2 TLSv1.3;

        # Long-term cache for third-party vendor SDK
        location ~* ^/vendor/.+\.(css|js|json|svg|woff2?)$ {
            expires 7d;
            add_header Cache-Control "public, immutable";
        }

        # No-cache for business JS/CSS — avoids serving stale code after deploys
        location ~* \.(css|js|json|svg|woff2?)$ {
            add_header Cache-Control "no-cache, must-revalidate";
        }

        location / {
            try_files $uri $uri/ /index.html;
        }

        # Service Worker must never be cached
        location = /sw.js {
            add_header Cache-Control "no-cache, no-store, must-revalidate";
        }

        gzip on;
        gzip_types text/plain text/css application/javascript application/json;
    }
    ```

    Test the configuration syntax before reloading:

    ```bash
    sudo nginx -t && sudo systemctl reload nginx
    ```
  </Step>

  <Step title="Obtain a Let's Encrypt certificate with Certbot">
    With the `server_name your-domain.com` block in place and DNS resolving to the server, run:

    ```bash
    sudo certbot --nginx -d your-domain.com
    ```

    Certbot will prompt for an email address, ask you to accept the terms of service, and then automatically install the certificate and update the Nginx configuration. On success the certificate files are located at:

    ```text
    /etc/letsencrypt/live/your-domain.com/fullchain.pem
    /etc/letsencrypt/live/your-domain.com/privkey.pem
    ```

    Certbot installs a systemd timer or cron job for automatic renewal. Verify it works with:

    ```bash
    sudo certbot renew --dry-run
    ```
  </Step>
</Steps>

<Note>
  If you see a warning like `the "listen ... http2" directive is deprecated` when running `nginx -t` on Nginx 1.26+, replace `listen 443 ssl http2;` with two separate directives: `listen 443 ssl;` and `http2 on;`. The template in `deploy/nginx.conf` already uses the new syntax.
</Note>

## Phase 5 — Deploy frontend

<Steps>
  <Step title="Create config.js on the server">
    The deploy script intentionally **never uploads** `config.js` — it is listed in the rsync exclusions to prevent accidentally overwriting a production configuration or committing secrets to source control. You must create it manually on the server the first time.

    SSH in and create the file:

    ```bash
    ssh root@YOUR_SERVER_IP
    sudo nano /var/www/work-time-recorder/config.js
    ```

    The file contents must match your local `config.js` (copy from `config.example.js` if needed):

    ```javascript
    const APP_CONFIG = {
        CLOUDBASE_ENV: 'common-YOUR_ENV_ID',  // replace with your actual environment ID
        CLOUDBASE_REGION: 'ap-shanghai',
        // ... other settings
    };
    ```

    Set the correct ownership:

    ```bash
    sudo chown nginx:nginx /var/www/work-time-recorder/config.js
    sudo chmod 644 /var/www/work-time-recorder/config.js
    ```
  </Step>

  <Step title="Run the deploy script">
    From the project root on your **development machine**:

    ```bash
    chmod +x deploy/deploy-mainland.sh
    ./deploy/deploy-mainland.sh root@YOUR_SERVER_IP your-domain.com
    ```

    The script performs two operations:

    1. **rsync** — synchronises the project to `/var/www/work-time-recorder/` on the server, excluding the following paths:

       ```text
       .git  .github  .cursor  .vscode  node_modules
       cloudfunctions  docs  supabase  deploy  config.js  cloudbaserc.json
       ```

    2. **Permission fix** — SSHes into the server and runs `chown -R nginx:nginx`, sets directory/file modes to `755`/`644`, and applies the SELinux label `httpd_sys_content_t` if SELinux is in Enforcing mode.
  </Step>
</Steps>

<Note>
  `config.js` is excluded from every rsync run by the deploy script. It must be created and maintained manually on the server. If you update the CloudBase environment ID, SSH in and edit the file directly — no redeploy is needed as Nginx serves it as a static file.
</Note>

## Phase 6 — Verification checklist

Once the deploy script completes, run through the following checks to confirm the deployment is healthy:

- **HTTP response**: `curl -I https://your-domain.com/` should return `HTTP/2 200`.
- **No mixed-content errors**: open the browser developer console — there should be no warnings about insecure (HTTP) resources loaded on an HTTPS page.
- **Login / register**: create a new account and verify you receive the email verification code and are logged in automatically after registration.
- **Record sync**: create a work time record and confirm it appears in the CloudBase console under **Database → work_records**.
- **PWA install**: on a supported mobile browser, the "Add to Home Screen" prompt should appear and the installed app should open correctly.

## Troubleshooting

<AccordionGroup>
  <Accordion title="403 Forbidden after rsync">
    This happens when rsync uploads files as `root`, leaving Nginx unable to read them. Fix ownership and SELinux labels in one pass:

    ```bash
    sudo chown -R nginx:nginx /var/www/work-time-recorder
    sudo chmod 755 /var/www
    sudo find /var/www/work-time-recorder -type d -exec chmod 755 {} +
    sudo find /var/www/work-time-recorder -type f -exec chmod 644 {} +

    # If SELinux is in Enforcing mode (check with: getenforce)
    sudo chcon -R -t httpd_sys_content_t /var/www/work-time-recorder
    ```

    Alternatively, just re-run the deploy script — it applies the same permission fix automatically on every run.

    To diagnose the specific cause check the Nginx error log:

    ```bash
    sudo tail -20 /var/log/nginx/error.log
    ```

    A `Permission denied` entry points to file permissions or SELinux; `No such file or directory` points to a misconfigured `root` path in the Nginx site config.
  </Accordion>

  <Accordion title="Login fails or CORS / security domain error">
    CloudBase rejects SDK requests from origins not in its allowlist. Add your live domain to the CloudBase security domains list:

    1. Open the [CloudBase console](https://console.cloud.tencent.com/tcb) and select your environment.
    2. Go to **Security Configuration → Web Security Domains (WEB 安全域名)**.
    3. Add `your-domain.com` — **without** the `https://` prefix.

    Also confirm that `config.js` exists on the server and contains the correct `CLOUDBASE_ENV` value. Access the server via the domain (not via IP) when testing CloudBase functionality.
  </Accordion>

  <Accordion title="Old JavaScript still loading after a deploy">
    The browser's Service Worker may be serving a cached bundle. There are two remedies:

    1. **Bump `CACHE_NAME`** in `sw.js` — on the next page load the Service Worker will detect the version change, discard the old cache, and fetch fresh assets.
    2. **Force a hard reload** in the browser with `Ctrl+Shift+R` (or clear site data in DevTools → Application → Storage).

    The Nginx configuration already sends `Cache-Control: no-cache, must-revalidate` for all business JS and CSS files, so the browser will revalidate on every load once the Service Worker cache is cleared.
  </Accordion>

  <Accordion title="Certbot cannot install the certificate to Nginx">
    If Certbot reports something like:

    ```text
    Successfully received certificate.
    Could not install certificate
    Could not automatically find a matching server block for your-domain.com.
    ```

    The cause is that no Nginx `server` block with `server_name your-domain.com` exists yet. Certbot needs that block to know where to insert the certificate directives.

    Resolution:

    1. Create `/etc/nginx/conf.d/your-domain.com.conf` manually (use the `deploy/nginx.conf` template, replacing the placeholder domain).
    2. Run `sudo nginx -t && sudo systemctl reload nginx` to make Nginx load the new config.
    3. Re-run `sudo certbot --nginx -d your-domain.com`.

    Make sure the domain in `server_name`, the `-d` flag, and your DNS A record are **exactly identical** — even a trailing dot or a `www` mismatch will cause Certbot to skip the block.
  </Accordion>
</AccordionGroup>
